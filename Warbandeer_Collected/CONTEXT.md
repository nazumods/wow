# Warbandeer_Collected

**Deps:** LibNAddOn, LibNUI, LibNUI-ModelViewer, Warbandeer_Characters · **SavedVars:** `WarbandeerCollectedDB` (v8) · **Commands:** `/collected`, `/collect` (no-arg opens the window; `scan`; `wanted` lists wanted sets; `outfit export|post|import <string or link>|list` for `/customset` + chat-hyperlink interchange; `model <id>` / `scale <n>` / `normalize <0..1>` / `release <1..12>` / `coverage [all]` / `weapons [<category>]` dev verify) · **Reads:** `WarbandeerApi` · **UI:** LibNUI · **Compartment:** `WarbandeerCollected_OnAddonCompartmentClick` · **Exposes:** `WarbandeerCollectedApi` (data bridge for Warbandeer's `collected` view — reads scan data, reads + **writes** the wanted/rank ratings)

Transmog set collection tracker. Renders a class × instance-set grid showing, per character, how many appearances of each tier/dungeon set remain uncollected, plus per-character instance lockouts. Each class set also carries two account-wide, user-authored **ratings**: a **wanted** flag (your target list) and an **S–F tier rank** (a global baseline with optional per-race overrides) — see [Ratings](#ratings).

```lua
  illusionWanted = { [sourceID] = true },        -- illusion target list (per illusion sourceID)
  lastOutfit = customSetID | false,               -- v7, now unused (per-character id)
  outfits = { { name, look, char, class, forClass, armor }, ... },   -- the outfit library (#655)
                                                   -- (the row starts neutral; nothing is remembered)
```
- `true` = base set fully collected; otherwise a partial record (`parts` is the raw `GetSetPrimaryAppearances` array).
- The three rating tables are keyed by the **globally-unique base `setId`** (not nested under `groupId` like `sets`), so they're group-independent and survive a re-scan (`/collected scan` wipes only `sets`/`collected`/`total`). `raceId` is the canonical race id (`ns:PlayerRace()` / the dressing-room selector).
- `MigrateDB` is non-destructive: only ensures missing top-level keys exist (v3 adds `wanted`/`rank`/`raceRank`; v4 adds `dressPos`/`windowPos`; v5 adds `weaponWanted`; v6 adds `cosmeticWanted` + `illusionWanted`; v7 adds `lastOutfit`; v8 adds `outfits`; v9 adds `libraryPos`; v10 adds `weaponRank`). The bump is what seeds each table: `MigrateDB` runs only on a version mismatch, so a new rating table added without one would still be `nil` at its first write.

### Remembered window positions

`dressPos` (set-preview / dressing room) and `windowPos` (main window) hold each window's last dragged anchor as `{ point, relPoint, x, y }` (relative to `UIParent`). They're populated by `TitleFrame:RememberPosition(store)` (LibNUI), called once when each window is lazily built (`ns.ShowDressingRoom` / `ns:Open`): the helper restores the saved point right away and re-saves it on every drag-stop, so the windows no longer re-center after a `/reload` or relog (issue #179). Both tables start empty `{}` — an empty store leaves the window at its constructor default (centered). **Since #708** the dressing room and outfit library dock onto the collection window instead of floating free, so they no longer call `RememberPosition` (the dock reparents + anchors them to the host and their titlebars drag the host); `dressPos` is **dead but retained** — annotated as such at its `MigrateDB` seed (#769 L-12), kept because the DB rule is non-destructive (a user must be able to roll back a revision without data loss) and a cleanup belongs in an explicit command, never an automatic wipe. **`libraryPos` is live again as of #767 L-3**: the outfit library floats free when no collection window is on screen (opened from the game's transmogrifier, say), and `ns.UndockPanel` hands it that store so a free-floating library remembers where it was dragged — while docked it still has no independent position. `windowPos` persists the dragged position of whichever collection window is the dock host.

## Scan Logic (`/collected scan`)

Resets the three DB keys, then for each group → each set with an `id`:
- `C_TransmogSets.IsBaseSetCollected(id)` true → store `true`, bump `collected`.
- else → `GetSetPrimaryAppearances(id)`, count `p.collected`, store `{ collected, parts, total }`.

`total` accumulates `#grp.sets`. After scanning, refreshes `ns.window.counter` and `ns.window.data`. The rating keys (`wanted`/`rank`/`raceRank`) are **not** touched.

The scan body is the reusable `ns:Scan()` method (in `commands.lua`, silent); the `scan` command calls it then prints, the compartment right-click calls it, and a **`TRANSMOG_COLLECTION_UPDATED`** handler calls it (debounced via `self:delay(500, …)`, skipped until the first manual scan) so the counts/grid update live when you learn an appearance. After refreshing its own window, `ns:Scan()` fires the **`API:OnScanned`** subscribers (`ns._scanned`) — Warbandeer's collected view registers one to re-render in sync, reading the now-fresh DB with no debounce race.

## Ratings

Two account-wide, user-authored attributes per class set, independent of each other and of collection status:

- **Wanted** — a boolean target list. Toggle by Shift-clicking a grid cell (`/collected` window or Warbandeer's `collected` view) or the dressing room's **Wanted** button. Surfaced as a gold star on the cell, an `★ N` window counter, the InfoTip status line, the `/collected wanted` chat list, and a **Wanted only** grid filter that shows only rows holding a wanted set (non-wanted class cells within a shown row still blank; when nothing is flagged, a centered "You don't have any Wanted sets." message via `DataView:_setEmpty`). **Since #768 L-5 the empty state shows for ANY empty result, not just the ★ filter** — an expansion × category combination matching nothing used to collapse the grid to its bare header with no message and no reserved height, reading as broken rather than narrow. The wording branches on `_wantedOnly` so it still says *why* it's empty ("No sets match these filters." / "No weapon looks match these filters.").
- **Rank** — an `S/A/B/C/F` aesthetic tier. A single **baseline** per set plus optional **per-race overrides** (the same look reads differently on different races). Edited only in the dressing room (it has the race selector): the tier buttons write the baseline, or the override for the selected race when **This race** is active. `ns:EffectiveRank(setId, raceId)` resolves override → baseline → nil; grids render the effective rank **for the logged-in character's race** as the tier letter in its tier color (top-right of the cell), and the InfoTip shows it too (`(race)` when an override applies).

Model + accessors live in `ratings.lua` (on `ns`); `api.lua` forwards them to consumers since the DB is account-wide. The shared dressing room and the `DataView` grid (rendered both in Collected's own window and embedded in Warbandeer's `CollectedView`) all read/write the same data.

The **Weapons view** carries its own parallel Wanted list — `db.weaponWanted`, keyed by appearance `visualID` (`ns:IsWeaponWanted`/`ToggleWeaponWanted`/`WeaponWantedCount`) — toggled by shift-clicking a row in the drill-in chooser, **not** by the room's ★, which rates the previewed armour set whether or not a weapon is browsed (#673). The **cosmetic picker** carries a third — `db.cosmeticWanted`, same visualID key (`ns:IsCosmeticWanted`/`ToggleCosmeticWanted`/`CosmeticWantedCount`) — and the **illusion list** a fourth, `db.illusionWanted`, keyed by illusion **sourceID** instead (`ns:IsIllusionWanted`/`ToggleIllusionWanted`/`IllusionWantedCount`): illusions have no visualID, and the id spaces overlap numerically, so a shared table would eventually star the wrong row. Both are toggled by **shift-clicking a row** and shown as that row's ★. It gets its own table rather than sharing `weaponWanted` so a wanted shirt can't inflate `WeaponWantedCount` or surface in a Weapons-view filter. **Weapons carry a tier too** (#688) — `db.weaponRank`, same `visualID` key (`ns:WeaponRank`/`SetWeaponRank`), set from the chooser's own S–F row and **without** a per-race override, a weapon looking identical on every race. Both surface in the Weapons **grid** (#689): a cell is starred when any look in its (source × type) bucket is flagged and pipped with the best tier in it (`ns:WeaponCellWanted`/`WeaponCellRank` → `WeaponViewMarks`), the strip carries the armor grid's ★ **wanted-only** filter, and each host's header tally switches units with the mode. Only the *shirt/tabard* and *illusion* lists remain wanted-without-a-tier: neither has a grid to rank in.

## Gotchas

- **Never size a grid column from `label:Width()`.** A cell label is `SetAllPoints` to its cell, so `Width()`/`GetWidth()` returns the *anchor-derived* width the moment WoW has flushed layout — 0 for the name column, which is declared `width = 0` and only widened by the fit. A constructor-time measurement therefore returns the text width or 0 depending on whether a layout pass happened to run first, which is the login-only blank name column in #718. Use `Label:UnboundedWidth()` (`GetUnboundedStringWidth`), which measures the string and is layout-order independent — that's what `ns.FitNameCol` and `TableFrame:Autosize` both do. Both grids re-fit on the next frame (`C_Timer.After(0, ...)`) and again on `OnBeforeShow`, so a zero first pass self-repairs — but `FitNameCol` no-ops once a width has landed, so those retries cost nothing after the first success (walking every row on every show was a visible hitch on the Armor/Weapons swap). **The host actually acts on that "it grew" return as of #768 L-4:** both `_fitToGrid` implementations sized **height only**, so the deferred pass widened the grid and left the window narrow, clipping the rightmost column — and only `SetMode` re-widened, so Armor mode stayed clipped for the session unless you toggled to Weapons and back. Both now set width alongside height (and the embedded one calls `MainWindow:Fit()`, since a widened view inside an unchanged window is just clipped one frame further out), which makes `SetMode`'s own width line redundant. Note `Region:Show` fires `OnBeforeShow` *before* `_widget:Show()`, so that pass measures a still-hidden grid; it's a backstop, not the primary repair. **Known limitation:** the host sizes its window from the grid at construction only, so a repair that lands *after* that widens the column and the row area but not the window — names render, the right edge is tight until the window is rebuilt. Deriving the window width from the grid on every `onResized` was tried and reverted: the grids are anchored to both titlebar edges, so `grid:Width()` reports the window's own width back and the feedback wrecked the window's sizing (rows spilling outside it).
- **Grid cells show *uncollected* count, not collected** — `text = total - collected`, and the gradient shade is keyed by the *collected* fraction (`floor(collected/total*10)`), so a low number on a green cell means nearly done.
- **InfoTip slot order is fixed** — it walks slots `{1,3,15,5,6,7,8,9,10}` (Head, Shoulder, Back, Chest, Waist, Legs, Feet, Wrist, Hands — the `rowInfo`/`data` rows stay parallel to this list), matching `GetSourcesForSlot` against the set's primary `appearanceID`s; collected sources green, missing red. Back (cloak, slot 15) must be in this list or sets with a cloak silently drop it.
- **Trading Post / variant sets serve no per-slot sources.** `C_TransmogSets.GetSourcesForSlot(setID, slot)` returns empty for *every* slot on some sets (e.g. the Trading Post recolors, group `id` 47's `(Trading Post)` entry) even though `GetAllSourceIDs(setID)` still has all the pieces and the model wears them. Both the dressing-room slots and the InfoTip fall back to `ns.SetSlotPieces(setID)` (in `DressingRoomSlots.lua`), which buckets `GetAllSourceIDs` into slots by each piece's `GetItemInfoInstant` equip location.
- **Lockout state lives in the data layer**, not here — read via `api.GetAllCharacters()` → `toon.instances.locks[group.instance][group.difficulty]`.
- **`ns:CompartmentClick`**: right-click runs the scan, any other click opens the window.
- **DataView auto-sizes the name column** at construction from the widest row label, then grows `rowArea`/self to match.
- **Rating overlays refresh after the table rebuilds, not during it.** `DataView` overrides `update()` to call `TableFrame.update(self)` then `_refreshMarks()`. But the constructor-time `update()` (from `TableFrame:onLoad`) runs *before* the subclass's `update` is mixed onto the instance (see the `Class` Mixin order), so it'd skip marks — hence the constructor calls `self:_refreshMarks()` once explicitly at the end. Cells persist across re-sorts, so their `_wantStar`/`_rankPip` children persist too and are just shown/hidden.
- **Marks read live DB, cells carry only the `setId`.** A wanted/rank change only needs a `_refreshMarks()` (or a single `_applyCellMarks(cell, setId)` for the toggled cell) — no `GetData()` rebuild — *unless* the wanted-only filter is active, where the toggled set must appear/disappear, so those paths rebuild.
- **Arbitrary races need a `ModelScene` actor, not a bare `DressUpModel`.** `SetCustomRace` was removed, and `DressUpModel:SetDisplayInfo` renders non-player races untextured (white). The `ui.Model` widget borrows dressup scene 596 and skins its actor via `SetModelByCreatureDisplayID` (exact race+gender, needs a display ID) or `SetModelByUnit("player", …, customRaceID)` (any race, textured, gender = the char's). `ns.RaceModels` only supplies the former; it is hand-maintained and unverified beyond the Allied Races ids — verify in-game.
- **InfoTip show/hide is immediate.** Cell `onEnter` re-anchors and renders right away; `onLeave` hides at once. (An earlier version debounced reposition and deferred the hide so a **Preview** button inside the tip stayed clickable — both removed; the dressing room now opens only from the grid cell's `onClick`.)
- **Docking a panel to a window = a child `Frame` + a strip that `setDragTarget`s the host — NOT reparenting an existing window.** A frame follows another frame only through an *anchor* (`SetPoint`), never through parentage (`SetParent` cascades show/hide, alpha, scale, strata, clamping — not position). Both `TitleFrame` drag paths (`makeContainerDraggable` on the body, the titlebar's `dragTarget`) call `StartMoving()` on the **same** `self._widget`, and `TitleFrame:RememberPosition` re-anchors that widget to `UIParent` on restore *and* hooks `OnDragStop`/`OnMouseUp` to save a `UIParent`-relative point — so trying to dock an independent `TitleFrame` by reparenting/anchoring it after the fact is undone the moment the panel (or a reopen/restore) fires those handlers. The look builder pane docks correctly because it is a plain child `Frame` (`parent = room`) with **no** `drag`/`RememberPosition` of its own and a header `strip:setDragTarget(room._widget)` — grabbing the strip moves the room, and the anchored child follows (`controls/AppearancePicker.lua:104-136`). Reproduce *that* relationship to dock, don't reparent. (Feasibility study + plan for docking all three Collected windows: research issue #706; artifact `Research/2026-07-24/collected-window-docking`.)
- **`ItemTransmogInfo.appearanceID` is a *sourceID*, not a visualID.** The field name reads like an `ItemAppearanceID` but holds an **itemModifiedAppearanceID** — Blizzard's own code feeds it to `PlayerCanCollectSource` / `GetAppearanceInfoBySource`. That is the same currency `GetAllSourceIDs`, `_currentSources` and the look builder's `_lookMH`/`_lookOH` already deal in, so nothing converts on the way in or out; feeding it a `visualID` from `GetCategoryAppearances` instead is the mistake to watch for (resolve those through `ns.AppearanceSource` first).
- **The main-hand `secondaryAppearanceID` is a discriminator, not an appearance.** `-1` (`Constants.Transmog.MainHandTransmogIsIndividualWeapon`) means "an ordinary weapon"; `0` means "a paired Legion artifact — derive the off-hand from me". Set it through the mixin's `ConfigureSecondaryForMainHand`, never by hand, or the game invents an off-hand. It **must** be forwarded to `Model:SlotTransmog` on the main hand (#755). The rule here previously said the opposite — that the model would read it as an appearance id — which is wrong on both halves: `Model:SlotTransmog` passes `opts.secondaryAppearanceID` straight into `ItemUtil.CreateItemTransmogInfo`, where for the main hand it **is** this discriminator field (spelled out in LibNUI-ModelViewer's docstring/README/CONTEXT since #753). `AppearancePicker` had always ignored the stated rule; `DressModelFromList` followed it, which is exactly why a look loaded from the library rendered differently from the same look composed in the builder. The rule the code now follows: **shoulders forward a real split-shoulder secondary, the main hand forwards the paired-artifact discriminator (`ns.MainHandSecondary`, outfitmodel.lua — shared by both paths so they cannot drift again), every other slot forwards nothing.**
- **`GetCustomSetHyperlinkFromItemTransmogInfoList` THROWS on a bad list — it does not return nil, despite being documented `MayReturnNothing = true`.** So it must be gated, never called speculatively: an unguarded call surfaces a Lua error in the user's chat frame. `ns.OutfitHyperlink` gates on `ns.OutfitIssues` (`filled > 0 and not pending`), the same pre-flight the save path uses. Reading the error: the C binding's **argument index is off by one** against the documented signature (`GetCustomSetHyperlinkFromItemTransmogInfoList(list)` blames `#2`, `NewCustomSet(name, icon, list)` blames `#4`) — both times the offending argument is the `itemTransmogInfoList`, and the message names neither the slot nor the reason, so validate before calling rather than interpreting it. **Ownership is not the constraint**: a probe (#643) built a 113-character link from a loaded, character-valid, *unowned* source and round-tripped it losslessly. Still unpinned: whether `canCollect = false` alone reproduces the throw, using a source that is loaded but invalid for the character.
- **`Blizzard_TransmogShared` is `## LoadOnDemand: 1`.** So `TransmogUtil.CreateCustomSetSlashCommand` / `ParseCustomSetSlashCommand` / `GetEmptyItemTransmogInfoList` / `IsValidTransmogSlotID` may not exist when an addon file runs — `outfitcodec.lua` reimplements the ones we need rather than calling them (which also keeps it WoW-free and unit-testable). `ItemUtil` (`Blizzard_FrameXMLUtil`) is *not* LoD and is safe to call.
- **`SlotTransmog` overrides outlive a re-skin — deliberately for the look builder, dangerously for an outfit.** `Model` re-asserts every registered override after each async model load, which is exactly what keeps a composed weapon/illusion pick on the model across a race change or a set Step. An applied outfit registers overrides across the *armor* slots too, and those must be dropped when a set is loaded or the outfit repaints over it slot by slot — hence `:ClearOutfitArmor()` at the top of `_load`. The split to keep in mind when adding a slot: **set-supplied slots get cleared, composed-look picks (weapons, shirt, tabard) don't.**
- **`PlayerCanCollectSource`'s `canCollect` means "this character *is able to* collect it", NOT "has collected it".** Verified in game: nine sources the player demonstrably did not own all answered `hasData = true, canCollect = true, hasCollected = false`. **But it does NOT report armour-type/class validity either** — measured again 2026-07-22: on a Druid, with the wardrobe class filter correctly reading Druid (`GetClassFilter()` = 11 = `UnitClass`), a **plate** appearance still answered `canCollect = true`. So the flag distinguishes neither ownership nor wearability, and **an appearance you simply haven't collected yet saves fine**. Per-source ownership is a different flag — `AppearanceSourceInfo.isCollected`, the same one the paper-doll slots colour their green/red borders from. `ns.OutfitIssues` therefore reports **only** `pending` + `filled`; `ns.OutfitSummary` marks ownership as `(not owned)` and nothing else.
- **`ComposeOutfit` must follow the MODE, not `self._set`.** In outfit mode the armor on the model came from a loaded look while `_set` still points at the last set clicked in the grid, so composing from `_set` there returns a *different* outfit than the one on screen. That shipped in #642 and caused real data loss: Save overwrites the selected entry with the composed list, so re-saving a loaded look silently replaced it with the stale set's armor — two library entries ended up holding the same look. The armor half now reads `self._outfit` when set; the weapon and cosmetic slots always come from the look fields, in both modes, so a pick made *since* the load isn't discarded. The same staleness applies to provenance: `_outfitMeta` carries the entry's own `forClass` in outfit mode rather than deriving one from `_classIndex`. **It delegates `char`/`class`/`armor` to `ns.LocalOutfitMeta` and adds only `forClass`** (#770 step 4) — it used to re-derive all three identically, which is how a save surface ends up stamping provenance that quietly disagrees with the others (the failure mode behind #758), and it means a new save surface inherits provenance instead of hand-copying it.
- **The game's custom sets are PER-CHARACTER.** Measured 2026-07-22: five sets saved on one alt were absent on another, and **`id 0` resolved to a different set on each** — so each character has its own id namespace, not a shared store. That's why `outfitlibrary.lua` exists: a look can only follow you across characters if we keep it in our own account-wide SavedVariables, with `PushOutfit` copying one into the current character's sets when it's actually needed at a transmogrifier. *Compare ids and set membership, never names* — "TWW 1" existing on two characters looked like corroboration of the opposite conclusion and was just a name reused across alts.
- **Saving to a custom set does NOT drop anything — the slot-clearing is in Blizzard's UI layer, not the API.** `WardrobeCustomSetManager:EvaluateAppearances` clears slots failing `PlayerCanCollectSource` before *its* `NewCustomSet` call, so the behaviour is real but belongs to their frame, and a **direct** `C_TransmogCollection.NewCustomSet` never goes through it. Measured 2026-07-22: a plate set saved from a Druid round-tripped **complete**, every slot intact, and rendered in Blizzard's own Dressing Room. Two successive revisions of this file claimed otherwise (first "uncollected pieces are dropped", then "unusable pieces are dropped"); both were wrong, and the pre-flight they justified has been removed rather than reworded. **Wearing** such a set at a transmogrifier is a separate gate that may well refuse — but that's an *application* question, and `PlayerCanCollectSource` is not its signal (`C_Transmog.CanTransmogItemWithItem` and the slot-level checks are). Export is unaffected either way: the `/customset` string is just ids and round-trips anything.
- **Weapon cells are a parallel API surface — and the #516 armour-grid groups that used to share it are GONE (#653).** `data/weapons.lua` once put two `kind`-tagged rows (`illusion`/`arsenal`) in the ARMOR grid, scanned via `ns:_scanWeaponSet` off `C_TransmogCollection` and rendered through their own `_dressWeapon` branches and a native `weaponTip`. All of that is deleted: **arsenals** became ordinary `ns.WeaponSources` rows (`data/arsenals.lua` — 21 of their 23 appearances were already in the Weapons grid, unnamed, inside Legion → Vendor), and **illusions** were never a set — they live in the look builder's Illusions tab, with only their sourceID→class map surviving as `data/illusions.lua`. What remains of the parallel surface is the **weapon-cell** path: `ns.PreviewWeaponCell` builds a synthetic `weaponCell = true` group, and since #673 that flag routes `_load` to `_loadCell` (`controls/WeaponCellPreview.lua`) rather than selecting a render. **The second doll it used to select is gone.** `_dressWeapon` rendered the char's race on a BARE body holding one appearance, which forced the rest: it `ClearSlotTransmog`ed all four composed-look slots up front (an override outlives the re-skin, and with the look-builder's slots hidden there was no widget left to take anything off), `_showSlots(false)` + hidden tier bars stripped the armour chrome, and a weapon found here could only be *described* — `_useCellLook` printed "Added X to your look's main hand — preview an armor set to see it". All of it is deleted: a browsed weapon is now an ordinary pick in the composed look, on the doll the armour is on, so nothing is wiped, nothing is hidden, and there is nothing to say. `_stepWeaponPiece` (↑/↓) and `_stepWeaponType` (←/→) restage in place; `_titleWeapon` surfaces the look's real name, retitling async while item names load. **`group.kind` is gone as a discriminator — everything tests `group.weaponCell`.** Illusion owned-state still reads `GetIllusionInfo(sourceID).isCollected` with **hardcoded sourceIDs** (Razorice 5869, Poisoned 5364, Shaman brands 5871–5875) — **account-wide + cross-class**: `GetIllusions()` only enumerates the current char's *usable* illusions, so a name-match against it can't see other-class ones. The curated **How to obtain** line survived the move: it is now an `obtain` field on an arsenal row, appended by `ShowWeaponCellTip` — NOT the illusion API's `sourceText`, which traces each shimmer to the oldest item bearing it (Flametongue → Ragnaros) and so misleads. The **all-weapon-illusions** collection (Mongoose etc.) stays out of scope — class-agnostic + account-wide, so it never fitted the class grid.
